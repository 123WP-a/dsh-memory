## 一 为什么「多模态」这一条排在实测的最前面

设计者把多模态架构定位为**灵枢与世界模型的接入口**——这把文档 §4.4 的性质改变了：

- 文档里 D1（原始像素交付）原本只是「交付层四层改造」中的第四项，且 §7.1 把它排在**阶段 3（最后）**；

⇒ **本纲领的排序与文档 §7.1 不同，理由在此**：文档按「瓶颈律 + 改动面」排；本纲领按「**接入口是否已通**」排。**凡属接入口本身的缺口，优先取证。**

### 线 A · 接入口取证（**零 API 花费，批 1 子代理已回**）

> **★本节经过一次自我更正（2026-10-11 09:2x）。** 编排侧先自取了三条读数，其中 **A1 收窄、A2 判错**——子代理的完整取证推翻了它们。**两处更正都保留原判与推翻依据**，因为「我错在哪」比「正确答案」更值得留档。

**★A1（**更正**）：经 `assembly.contexts` 注入图像 —— 这条路不存在；但**另有两条路能注入**。**

原判（编排侧，仅读了 `AssembledContext` 类型）：**不能**。

`<D>/dsh-system-prompt/lib/types/index.d.ts:90-95`：


⇒ 这一层结论**仍然成立**：`contexts` 的每个元素只有 `name` 与 `text`，**没有 image part 槽**；本仓插件 `src/hooks.ts:642/:663` 的 `contexts.push({name, text})` 用的正是这个类型。

**但「所以插件不能注入图像」是错的。** 子代理枚举了 `<D>` 下全部 `declare module '@deepseek-ai/cordis' { interface Events }` 事件名（**88 个**），逐条核对载荷是否含 `ContentBlock[]`，结论：

**★A1 的根因（我的判据错在哪）**：我只读了**我们插件正在用的那一个钩子**（`system-prompt/assemble`）的类型，就从「这个钩子不收 image」推出「插件不能注入图像」。**判据的正确形态是「枚举全部可用钩子点、逐条核对载荷类型」，不是「检查我正在用的那个」。** 这与我在线 B 记的 B7（grep 多词混在一个模式里）是**同一类错误的两个面**：**从局部读数推出全称结论**。

**★A2（**更正**）：图像块存在且只许走 user message / tool result —— 这两点成立；但「默认被 offload 成占位文本」**判错了，方向反了**。**

原判（编排侧，仅读了 `offloaded?: true` 的注释）：**原图交付不是默认路径，而是被 offload 挤掉的那条**。

**子代理实读 `requiredImageOffload` 的实现后推翻**（`<D>/dsh-llm/lib/types/content.js:183-226`）：

```js
const excessCount = budget.maxImages === undefined ? 0 : Math.max(0, lengths.length - budget.maxImages);
const excessBytes = budget.maxBytes  === undefined ? 0 : Math.max(0, total - budget.maxBytes);
if (excessCount === 0 && excessBytes === 0) return 0;     // ← 未超预算 = 0，不 offload
```

且触发链是**「报错 → 宿主补记 → 重试」**，不是默认投影（`dsh-llm-deepseek/lib/index.js:1435-1438`）：

```js
if (offloadImages > 0) throw new LlmError(`... ${offloadImages} more oldest occurrence(s) must be offloaded.`, IMAGE_OFFLOAD_REQUIRED_CODE, { offloadImages });
```

再由 `dsh-compaction-image-offload` 监听 `agent/request-error`、记 `image/offload` 事件后返回 `{kind:"retry"}`。

⇒ **正确的判定：原图交付是默认路径。** 正常路径先走 Files API 上传（`prepareFileIds`，`:1445-1458`），Files 失败才降级内联 base64；`offloaded: true` **只**在收到 `IMAGE_OFFLOAD_REQUIRED` 之后才由宿主写入。默认预算也宽松（DeepSeek 侧：`maxImagesPerRequest = 600`、`maxRequestFilesBytes = 128 MiB`、`maxInlineRequestImageBytes = 20 MiB`）。

**★A2 的根因（我的判据错在哪）**：我把 `offloaded?: true` 的**注释**（它描述的是「这条路径上会发什么」）读成了**默认行为**——而注释没说的恰恰是「什么时候会走到这条路径」。**⇒ 判据：注释描述的是「该分支的行为」，不是「该分支是否被默认走到」；判断默认路径必须读**条件判断**（这里是 `if (excessCount === 0 && excessBytes === 0) return 0`）。** 这与 A1 同根：**用描述性材料（类型定义 / 注释）代替了判定性材料（分支条件 / 事件枚举）**。

**⇒ A1/A2 更正对实测排序的影响（重要）**：原判「D1 落地 ≠ 原图到模型」**不成立** ⇒ **原图交付这条路比我以为的宽**。而「插件能不能把图送进去」的答案是**能（经 `agent/pre-step`）**，不是不能。⇒ 线 A 从「交付面基本被堵」变成「**交付面有两条可用通道，且默认就是原图**」——**这实质改变了批 3 的必要性排序**（见 §六）。

**★A3（已取证·且比原判更完整）：图像计费口径有宿主 API，且有真公式。**

原判只定位到接口（`LlmImageRequestPricing.priceImages`，`<D>/dsh-llm/lib/types/types.d.ts:183-203`）。子代理找到**实现**（`dsh-llm-deepseek/lib/index.js:56-121`、`:272-286`）：

- **按尺寸分档，非固定值、非纯像素线性**：`PATCH_SIZE=14` → `DOWNSAMPLE_RATIO=3`（即 42px 一个 token 单元）→ 单图上限 `MAX_IMAGE_TOKENS=1024`、下限 `MIN_PIXELS=544*544`（小于此等比放大）；
- 每格 token 数 `gridHeight*(gridWidth+1)+2`（每行 1 分隔符 + 2 框定）；
- 迭代到不动点（最多 10 次），超上限时用闭式解取最大保比网格；
- **`offloaded` 的块计 `visualTokens: 0`** ＋ 占位文本按文本估价；
- 消费方：`dsh-token-meter` 的 `priceSurface`，最终口径 ＝ `visualTokens + estimateContent(占位文本)`。

⇒ **文档 §4.4 判据②「图像计费口径未取证」正式撤销**，并可直接引用上述公式做预算估算。

**★A4（新增·决定性）：工具结果**能**回传图像，且宿主已有生产工具在这么做。**

`<D>/dsh-tool-fs/lib/index.js:955-963` 的 `read_image` 直接返回 image 块：


⇒ **「模型主动取图」这条路存在，且是宿主原生能力**——这比「被动注入」更强：**模型可以自己决定何时取哪张图**。⇒ 文档 §4.4 的「图像通道必须另设一格」应改为**复用宿主既有的 tool-result 图像通道**。

**★A5（新增·对本仓插件最直接）：用户贴图时 `ImageBlock` 确实出现，而本仓插件把它静默丢了。**

- 前端 `session/prompt` 端点接受 image part（`dsh-api-session-controller/lib/typert.host.js:788-795`），服务端经 `ctx.attachments.admitPromptContent(...)` 转成 `{type:'image', attachment}` 后建 user 消息（同包 `lib/index.js:861-877`）；

⇒ **★实测结论：用户只贴图不打字的消息，本插件完全无痕**（不进知识面、不进窗口）。**这比文档 §4.4 说的「非文本块入口即蒸发」更具体**：不是「存下来但没检索」，而是**连落盘都没有**。

**★A6（新增·B2 的宿主侧好消息）：宿主已在准入阶段做图像归一化与 EXIF 方向处理。**

`ImageAttachmentRef` 带 `originalDimensions`（注释：「Input dimensions after applying **EXIF orientation** and before normalization scaling」），admission 有 9 类错误码（`TOO_MANY_IMAGES`／`UNSUPPORTED_IMAGE_TYPE`／`INVALID_IMAGE_BASE64`／`IMAGE_TOO_MANY_PIXELS`／…）。⇒ **B2 的图像脱敏判据可以复用宿主已做的归一化**（不必自己重做方向修正）。

### 线 D · 阶段 1 两 oracle（**需 API 预算，待裁**）

R-oracle（绕过检索直喂相关节点原文）／D-oracle（保留真实检索只换交付层），最小可行版 100 题（约 300 次 reader 调用）。

## 六 批 1 收口后的站位（给下一批的判据依据）

## 七 本纲领自身的一次自我更正（留档）

**批 1 的编排侧预判被自己的子代理推翻了两处**，两处同根，记在这里当判据：

| # | 我的原判 | 实况 | 我错在哪 |
|---|---|---|---|
| A1 | 「插件不能注入图像」（因为 `assembly.contexts` 是纯文本） | **能**——`agent/pre-step` 与 `tools/post-execute` 都能写 `ImageBlock` | **我只读了「我们正在用的那一个钩子」，就从它推出全称结论**。正确形态＝**枚举全部可用钩子点、逐条核对载荷类型** |
| A2 | 「原图交付不是默认路径，是被 offload 挤掉的那条」 | **反了**——**原图交付是默认路径**，offload 是超预算后报错触发的事后纠错 | **我把注释（描述该分支的行为）读成了默认行为**；注释没说「什么时候会走到这条分支」。正确形态＝**读条件判断**（`if (excessCount === 0 && excessBytes === 0) return 0`） |

**⇒ 共同根因：用描述性材料（类型定义／注释）代替了判定性材料（分支条件／事件枚举）。** 这与我在同批记的 **B7**（把三个词混进一个 grep 模式、却报「命中来自哪个词」）**是同一类错误的两个面**：**从局部读数推出全称结论。**

**★判据（可复用）**：**「某能力不存在」这个结论，只能由「枚举了全部候选点、逐条核对」得出，不能由「我检查的那一个不支持」得出。** 而「默认走哪条分支」只能由**条件判断**读出，不能由**注释**读出。
