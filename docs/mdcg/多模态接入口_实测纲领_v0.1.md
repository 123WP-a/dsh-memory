## 一 为什么「多模态」这一条排在实测的最前面

设计者把多模态架构定位为**灵枢与世界模型的接入口**——这把文档 §4.4 的性质改变了：

- 文档里 D1（原始像素交付）原本只是「交付层四层改造」中的第四项，且 §7.1 把它排在**阶段 3（最后）**；
- 但若它是**接入口**，那么它的**前置三件**就不是「最后做」，而是**所有跨模态实测的准入条件**——在图像进不了库、也进不了注入面之前，任何「灵枢能不能用世界模型的输出」的实测都无从谈起。

⇒ **本纲领的排序与文档 §7.1 不同，理由在此**：文档按「瓶颈律 + 改动面」排；本纲领按「**接入口是否已通**」排。**凡属接入口本身的缺口，优先取证。**

## 二 四条实测线（按准入关系排，不按成本排）

### 线 A · 接入口取证（**零 API 花费，立即跑**）

文档三处标「未取证」的宿主能力，全部集中在接入口上。**编排侧已先取证三条（读数如下），余下交批 1 子代理补全**：

**★A1（已取证·判定＝不能）：经 `assembly.contexts` 注入图像 —— 这条路不存在。**

`<D>/dsh-system-prompt/lib/types/index.d.ts:90-95`：

```ts
export interface AssembledContext {
    /** The contributing context's unique name. */
    name: string;
    /** The resolved text before variable interpolation. */
    text: string;
}
```

⇒ **`contexts` 的每个元素只有 `name` 与 `text` 两个字段，没有 image part 槽。** 本仓插件 `src/hooks.ts:642/:663` 的 `contexts.push({name, text})` 用的就是这个类型。**图像不能经此进入模型请求。**

**★A2（已取证·部分通）：图像块存在，但只许走 user message，且默认被 offload 成占位文本。**

`<D>/dsh-llm/lib/types/types.d.ts:61-71` 的 `ImageBlock` 注释原文：

> A durable raster image reference, valid in user or assistant content. The block is deliberately role-neutral; assistant-side rendering is forward compatibility — **the current production adapters declare text-only output, so only user messages may carry images.**

同文件 `:72-82` 的 `offloaded?: true` 注释：

> Derived from a durable image-offload decision or preserved by a message rewrite. **Every route sends placeholder text naming the image and its available read-only path instead of image bytes.**

⇒ **原图交付（D1）在宿主里不是默认路径，而是「被 offload 挤掉」的那条**。这直接改变文档 §4.4 的成本判断：**不解决 offload 预算，D1 落地后拿到的仍是占位文本**。

**★A3（已取证·不再是「未取证」）：图像计费有宿主 API。**

`<D>/dsh-llm/lib/types/types.d.ts:183-203`：

```ts
export interface LlmImageRequestPrice {
    /** Provider visual tokens for the retained request image; 0 when only text represents this occurrence. */
    visualTokens: number;
    /** Model-visible text sent for this occurrence, to be priced by the caller's text estimator. */
    text: string;
}
export interface LlmImageRequestPricing {
    priceImages(images: readonly ImageBlock[]): readonly LlmImageRequestPrice[];
}
```

⇒ 文档 §4.4 判据②「图像计费口径未取证」**可撤销**：宿主提供 `priceImages`，由适配器实现。**实现公式待批 1 子代理补齐**（接口在，实现位置未定）。

**★A3′（新增发现）：宿主有现成的附件基础设施。** `<D>/dsh-attachment`（含 `dsh-attachment-local`）提供 `ImageAttachmentRef`（`attachmentId`／`mediaType`／`bytes`／`width`／`height`／`name?`／`originalDimensions?`）与 `FileAttachmentRef`，并有 admission 限额与 9 类错误码；另有 `dsh-compaction-image-offload` 包。

### 线 B · 写入面缺口（**零 API 花费，批 1 子代理已回**）

**★B3 已取证（身体库模态承载力）——结论比文档假设的更硬：图像「能进库」，但「不能按图像被检索或消费」。**

| 问 | 读数 | 判据 |
|---|---|---|
| `modality` 是记录字段还是判据维度？ | **记录字段** | 写入赋值 **10** 处；作筛选条件 **2** 处（`core.py:1088` SQL 级 ＋ `:5306` Python 级）；**生产调用方传该条件者 = 0 处**（`query_nodes` 的 13 个调用点、`query_by_semantics` 的 0 个调用点，**无一传 `modality=`**） |
| 存储层是否按模态分流？ | **不分流** | 单表 `nodes`，`modality TEXT` 是**普通列**（`core.py:766-784`）；索引只建了 `layer`／`edges` 两处（`core.py:811-813`），**modality 无索引**；无分表/分目录/分层 |
| 检索面是否按模态过滤？ | **不过滤** | `search_content`（`core.py:1574-1631`）判据链只看 `content`/`tags`/`importance`/`confidence`，**全程不读 `modality`**。**实测**：隔离库写入 `modality='image'` 节点后，`search_content('x')` **以 1.0 命中它**；同一查询同时返回 `['image','text']` 两种模态 |
| 非文本模态有专属检索入口吗？ | **没有可用的** | 唯一为图像设计的 `query_by_semantics`（`core.py:5297`，注释「语义→图像反向映射」）**零调用者**且默认无 provider 直接返回 `[]` |

**★B4 已取证（好消息）：`spatial_coordinates` 已是一个可复用的「区域锚」入口——多模态的锚定面不必新建。**

- `spatial_coordinates: Dict[str, float]` 已落盘，且**已有按坐标的检索路**：`spatiotemporal_query(center_node_id, time_radius, space_metric, space_radius)`（`core.py:1217-1251`），按命名轴差 ≤ 半径过滤。
- **实测**：center 在 `x=0.0`，`space_metric='x'`、`space_radius=0.5` ⇒ 召回 `x=0.1` 的节点、排除 `x=9.0` 的——**该路按坐标过滤、与 modality 无关**，可召回任意模态。
- 图像区域锚可直接落成既有形态（`subgraph_replace` 已是 `{"image2d_x":.., "image2d_y":..}`，`core.py:5729-5730`）。
- **局限（如实）**：只支持「**单轴差 ≤ 半径**」（`:1243`），**无 bbox／多边形／多轴联合范围查询**；`space_metric` 轴缺失则跳过（`:1241-1242`）；且与时间半径**强耦合**。
- ⇒ 文档 §4.3「缺区域级锚」这一条**须收窄**：锚的**存储与检索结构已在**，缺的是「区域」的**表达力**（单轴 vs bbox）与「id ↔ 载体位置」的**注入面**（4.1 的 id 注入）。

**★B5（新增缺口，文档未列）：world 侧无任何模块消费 `modality`。**

`lingshu/world/` 下**读** `modality` 的模块：**0 个**。读 `spatial_coordinates` 的有两处（`scene_model.py:378` 重建世界模型、`brain_store.py:515/:525` 读脑侧 `spatial.coords3d`）。⇒ **图像节点落库后，world 侧无人按模态读它**——这解释了为什么「图像进库」目前只是「存下来」。

**★B6（新增）：真视觉写入依赖仓外模块。** `core.py:5257` 的 `ingest_frame` 是**仓内唯一** `modality="image"` 写入路；而 `perceive_image`（`core.py:3576-3588`）`from vision import perceive_image` —— **`vision` 是仓外模块**（未装配时返回 `{"status":"vision_unavailable"}`）。⇒ 「图像进库」的**端到端**路径有一半在仓外。

**★B7（修正编排侧自己写错的一处线索）**：本纲领初稿写「`wm_simloop.py` 是 `lingshu/world/` 下唯一含 image 字样的文件」——**实测未复现**：该文件 `image`（忽略大小写）出现 **0** 次，`git grep -i image` 返回空，`git log -S image` 对该文件无任何提交；它唯一的模态痕迹是 `:579` 的 `"modality": "text"`。**根因＝我初稿的 grep 把 `image|multimodal|modality` 三个词混在一个模式里，命中其实来自 `modality` 而非 `image`。** ⇒ **判据：把多个词放进一个 grep 模式后，报「命中来自哪个词」前必须分模式重跑一次。**

**★B8（新增，且对世界模型接入口最关键）**：world 侧**确有图像原语处理模块**（`vprim.py` 的类别+bbox、`world3d.py` 的 2D bbox→3D 反投影、`multiview.py` 的多视角三角化、`silhouette3d.py`/`skeleton3d.py`/`scene_model.py` 的 PIL 渲染）——但它们**不读节点 `modality`、也不往库里写 `modality='image'`**。⇒ **「世界模型的图像能力」与「记忆库的模态面」目前是两条不相交的路**：这正是设计者所说「接入口」要打通的那条缝。

**⇒ 线 B 的能红条件（已命中，比预置的更重）**：B3 显示**模态不进检索判据**、B5 显示**world 侧不消费模态** ⇒ 「图像进库」当前**只是存下来、检索不到、也没人用**。⇒ 线 B 的产出须从「判据设计」扩为**三条**：①写入面装载判据（B1）②图像脱敏判据（B2）③**模态进检索判据的入口设计**（B3 新暴露——否则装载了也没用）。**第三件是本轮新增的发现，文档未列。**

### 线 D · 阶段 1 两 oracle（**需 API 预算，待裁**）

R-oracle（绕过检索直喂相关节点原文）／D-oracle（保留真实检索只换交付层），最小可行版 100 题（约 300 次 reader 调用）。

**这项与多模态的关系是间接的**：它定的是「瓶颈在 R 还是 D」——若结论是「瓶颈在 D」，则多模态交付（把原图/原文直交）正是 D 的解法，多模态路线得到理论支持；若结论是「瓶颈在 R」，则**先修检索**，多模态交付的收益上界受检索限制。

**待裁**：文档 §7.3 第 1 条（100 题 vs 500 题）——**这是算力预算，属决策面，我不代裁**。

## 六 批 1 收口后的站位（给下一批的判据依据）

**三句话**：

1. **交付面**（线 A）：`assembly.contexts` 是纯文本 ⇒ **「经注入面交付图像」这条路不存在**；`ImageBlock` 只许走 user message 且**默认被 offload 成占位文本** ⇒ **D1 落地 ≠ 原图到模型**。**须先解决 offload 预算，或改走工具面取图**（取决于宿主侧子代理对 A2/A4 的结论）。
2. **写入面**（线 B）：图像**能进库**（`ingest_frame` 已实现 `modality='image'`），但**模态不进任何检索判据**、**world 侧零消费** ⇒ 「进库」当前只是**存下来**。
3. **★接入口的缝在哪（本批最有价值的定位）**：不在「灵枢有没有图像能力」——world 侧有 vprim／world3d／multiview／silhouette3d 等**成熟图像原语模块**；也不在「能不能存」——`nodes` 表能存、`spatial_coordinates` 能锚。**缝在两侧没有共同的数据形态**：world 侧处理 bbox/图像但**不写库**，记忆库存 `modality` 但**不参与检索**、world 侧也**不读**。

⇒ **下一批的判据依据**：打通接入口的**最小可判动作**不是「加图像处理」也不是「加存储」，而是**让两侧共用同一个数据形态**——即「图像节点 + 区域锚（`spatial_coordinates`）+ 可检索（模态进判据或至少可被 world 侧按模态取）」这一条链。**这条链的每一环都已有结构（B4 已证 `spatial_coordinates` + `spatiotemporal_query` 可用），缺的是把它们接起来。**
